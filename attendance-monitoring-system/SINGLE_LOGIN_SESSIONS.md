# One active login per account

A successful explicit sign-in or email verification/recovery callback activates its Supabase session for the account. It replaces the previous app session only if Auth's stored session creation time is newer. Every authenticated API request checks the verified token's user and session ID against that active session. Old access tokens and refreshes cannot reclaim access. Same-browser tabs sharing the same Auth session are one login; this policy prevents separate PC/phone/browser sessions from remaining active together.

An open foreground page checks session validity every 20 seconds and when it becomes visible or reconnects. A replaced session loses API access immediately and the old page shows a sign-in message on its next request or heartbeat. Camera and workspace state are disposed when that happens. Offline or background pages may keep their previously rendered view until they reconnect or become visible; they cannot perform authenticated actions using the replaced session.

The private `app_private.login_session_started` function is a narrowly scoped, read-only SECURITY DEFINER helper because service_role cannot read managed Auth tables. It returns only the start time of one matching user/session pair if it is still present and unexpired. Its schema is private, search_path is empty, and execution is revoked from PUBLIC, anon and authenticated. No broad Auth-table permissions were granted. The public session function is SECURITY INVOKER and service-only; the server calls it only after Auth.getUser validates the token and its subject. Temporary password-verification sessions do not activate or displace the normal login.

The page initially shows a session-loading state rather than a sign-in form. Auth restoration finishes before choosing workspace, approval/privacy screens, or sign-in. Catalog failures do not discard login state, and temporary restoration failures offer Retry without clearing saved credentials. Bootstrap loads portal listeners before initializing Auth. Clicking the logo inside a workspace navigates to the role's dashboard without reloading.

Validation includes unit tests, rollback-only `tests/single-active-session.sql` under service_role, an opt-in two-client demo login test (`TEST_SINGLE_SESSION=1` plus `TEST_BASE_URL`), and isolated browser checks for refresh, logo navigation, catalog failure, and replaced-session feedback. Only demo sessions were used for live login tests; no attendance or real-account decisions were changed.
